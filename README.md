# GDR 대진표 · 경기 기록

대포클럽 개인 레포 `felix-mr/daepo-tennis`의 날짜별 기록, 고정 ID, 승점 집계 방식을 참고한 GDR 전용 웹 앱. 대포의 데이터와 Firebase 설정은 복사하지 않았다.

## 기존 기록 적재

2026-10-07 `guldari/(default)`에 29개 문서를 생성하고 전부 다시 읽어 검증했다. 원본 Numbers 2개에서 비어 있지 않은 값 1,675개를 셀 좌표와 원본 파일 SHA-256으로 보존했다. 정규화 집계 13개에 통산 개인 28명, 페어 260개, 하반기 12명, 연도 미확인 7회차/63개 개인행, 정정 전 10/4와 정본·검토 상태를 보관했다. 원본 파일·추출값·수신 기록은 `output/history/`에만 남기며 Git에 포함하지 않는다.

사용자가 확인한 2026-10-04 실제 경기 8개는 `sessions/2026-10-04`, 라운드 4개, `matchResults` 8개로 적재했다. 심진우는 득 16/실 14/+2, 전체 득실은 각각 154. 기본 모임 시간 19:00–21:00과 코트별 텍스트 순서를 라운드로 해석한 근거를 별도 보관했다. 실제 경기에서 분기 순위를 다시 계산하며, 이전 누적표를 함께 더하지 않는다. 기존 내부 상대 구성 계산은 이 실제 경기만 반영하며 통산 참고 가중치는 아직 적용하지 않았다.

- `clubs/gdr/historySources/{id}`: 원본 파일명·체크섬·표 크기·셀 좌표별 원본 값.
- `clubs/gdr/historySets/{id}`: 별도 기준일과 검토 상태를 가진 개인·페어·날짜별 집계.
- `clubs/gdr/historyImports/{id}`: 완료 수신 기록·내용 체크섬·건수.

위 경로는 조회만 허용하며 앱에서 생성·수정·삭제할 수 없다. 프로젝트 관리자 권한으로만 적재한다. 새로운 읽기 규칙은 `firebase/firestore.rules`에 준비했으며 실제 프로젝트 게시 전이다.

`node scripts/prepare-history.js`는 로컬 검토 자료에서 적재 계획을 생성한다. `scripts/import-firestore.js`에 `--account`, 설치된 Firebase CLI 디렉터리의 `--firebase-cli`를 지정하면 로그인 계정의 권한으로 읽기 사전 확인을 수행한다. `--apply`를 명시해야 변경한다. 기존 동일 문서는 건너뛰고 다른 내용이면 중단한다. 신규 문서만 `exists:false` 조건의 원자적 commit으로 생성해 재시도나 동시 입력이 기존 점수를 덮어쓰지 않는다. 자격 증명은 출력·공개 저장하지 않는다.

## 실행

```sh
npm install
npm run dev -- --port 5173
npm test
npm run build
```

`dist/`를 정적 호스팅에 게시할 수 있다. 하위 경로 배포도 지원한다. 공개 레포: `felix-mr/gdr-tennis`. GitHub Pages는 `gh-pages` 브랜치의 빌드 결과를 게시한다. 배포 주소: https://felix-mr.github.io/gdr-tennis/

업데이트 게시: `npm test`로 확인한 뒤 `npm run deploy`. 로컬 `.env.local`의 Firebase 연결 설정으로 빌드해 임시 checkout에서 `gh-pages` 브랜치에 일반 푸시한다. 배포 파일만 올리며 소스 브랜치는 건드리지 않고 강제 푸시하지 않는다. `.env.local`은 커밋하지 않는다. Pages 게시와 Firestore 접근 규칙 반영은 별도다.

자동 배포 템플릿은 `scripts/pages-workflow.template.yml`에 보관했다. 현재 GitHub OAuth 인증에 `workflow` scope가 없어 `.github/workflows` 파일 푸시가 거부되므로 우선 브랜치 게시 방식을 사용한다. 자동 배포로 전환하려면 인증에 `workflow` 권한을 추가한 다음 템플릿을 `.github/workflows/pages.yml`로 옮기고 Pages의 Build source를 GitHub Actions로 바꾼다. GitHub Actions secrets에는 Firebase 설정 4개가 등록되어 있다. 템플릿은 연결 설정이 빠진 빌드를 실패시킨다.

## 운영

- 전체 클럽 멤버 24명, 2026년 4분기 멤버 14명. 회원 ID와 분기 참여 명단을 분리하며, 모임 날짜의 분기 명단에서 참석자를 선택한다. 명단이 없는 분기는 새 대진 생성을 보류한다. 저장된 모임의 당시 멤버는 이후 명단 변경에도 조회에 유지한다. 최지원의 실제 성별은 유지하지만 전원 같은 복식 풀로 대진·순위 계산.
- 참석 선택에서 `게스트 +`로 이름을 입력하고 선택·제외·삭제할 수 있다. 이름은 1~12자, 중복 없이 모임당 최대 8명. 게스트도 최소 2경기를 배정하며 대진·휴식·경기 수·기록·이미지에 이름을 표시한다. 회원 분기 순위에는 포함하지 않는다.
- 2면. 기본 모임 시간은 일요일 19:00~21:00. 날짜별 시작·종료 시간을 같은 날 안에서 30분 단위로 변경할 수 있다. 경기 시간은 30분 고정, 목표 경기 수 입력 없음.
- 개인별 경기 수는 그날 참석자와 코트·모임 시간으로 계산한다. 4경기 상한 없음. 자동 배정의 당일 경기 수 차이는 최대 1경기. 복식 출전 총합은 4의 배수로 맞춘다.
- 과거 누적 경기 수로 당일 출전을 늘리거나 줄이지 않는다. 추가 경기의 동률 순서는 무작위로 정한다. 분기 경기 결과는 내부 팀 배정값 추정에만 사용한다.
- 참석자 모두 최소 2경기를 할 수 없으면 모임 시간을 늘리도록 안내한다. 수동 조정도 최소 2경기부터 가능하다. 참석자 4~7명은 한 번에 한 코트, 8명 이상은 두 코트를 사용한다.
- 첫 화면은 대진표 탭이며 메뉴를 화면 상단에 배치한다. 생성한 대진은 참석·시간 설정을 접고 바로 보여준다. 미리보기의 `참석·시간 수정`으로 설정을 다시 열 수 있으며, 개인 경기 수 확인·조정은 경기표 아래 접이식 영역에서 제공한다.
- 생성 후 개인 경기 수를 2~설정 시간의 라운드 수로 조정하고 다시 배정 가능. 실제로 시간 내 배정 가능한 조합만 확정. 19~22시 기준 4명은 각 6경기, 14명은 각 3~4경기다.
- 동시 중복 출전 금지. 파트너 중복·반복 상대·연속 휴식을 줄이는 탐색. 파트너 중복이 불가피한 배정은 횟수 표시.
- 같은 날짜는 한 모임. 확정된 팀 구성을 보존한다. 확정 이후 참가자·대진 변경 기능은 현재 제공하지 않는다.
- 점수 0~99 정수, 0:0 저장은 무승부. 미입력 경기는 순위에 포함하지 않는다.
- 승 3점·무 1점·패 0점. 같은 승점은 공동순위(1,1,3). 같은 승점 내 표시 순서만 득실차·이름순. 경기 없는 선수는 순위 `—`.
- 개인별 경기 수·승무패·승률·득·실·득실차. 승률은 승 / 전체 경기 수, 반올림 정수 %.
- 한국 날짜 기준 기본 분기. 현재 회원 회차는 2026-10-01~2027-01-01(종료일 제외). 과거 회차 명단과 기록 기간은 별도 확인해야 한다.
- 기간별 순위 CSV, 선수별 경기 기록, 인쇄, JSON 백업. 순위표의 이름을 누르면 `개인 기록` 화면으로 이동하며 멤버·조회 기간을 유지한다.
- `개인 기록`은 파트너별/상대 페어별 승·무·패, 승률, 득·실·득실차와 해당 경기 목록을 제공한다. 팀 A/B 순서와 상대 두 사람의 순서가 바뀌어도 같은 조합으로 묶는다. 게스트 신원은 날짜별로 구분한다.
- `개인 기록 → 이전 집계`에서 원본 기준일별 통산 개인·파트너, 하반기 누적, 연도 미확인 날짜별 집계를 조회한다. 오류·인물 잠정 연결·연도 미확인과 정정 전 값을 표시한다. 이전 멤버는 과거 조회에서 선택할 수 있으며 현재 참석 후보나 분기 명단에 추가하지 않는다.
- 대진 미리보기와 저장된 대진 모두 `이미지 저장·공유`에서 PNG로 만들 수 있다. 이미지에는 날짜·시간, 안쪽/바깥쪽 코트의 페어, 휴식 멤버, 개인별 경기 수를 넣는다. 저장된 대진은 입력된 점수를 함께 표시하며 미확정 대진은 이미지에 명시한다.
- 모바일은 미리보기 이미지를 길게 눌러 사진에 저장하거나 `이미지 공유`에서 카카오톡을 선택한다. 실제 공유 대상은 기기의 공유 메뉴가 제공한다. 파일 공유를 지원하지 않는 브라우저에서는 `파일 저장` 후 직접 첨부할 수 있다. 긴 대진은 8라운드씩 여러 PNG로 나눠 각 장을 저장·공유한다.
- 순위·기록 화면은 상반기(1~6월)·하반기(7~12월) 조회도 제공한다. `기록 이미지 2장`에서 완료 기록이 있는 날짜를 선택하면 당일 개인 결과표와 해당 조회 기간의 선택 날짜까지 누적 순위표를 PNG 두 장으로 만든다. 미래 경기 결과는 선택 날짜 기준 누적에 포함하지 않는다. 게스트와 경기 없는 회원은 결과 이미지에서 제외한다. 지원하는 모바일 공유 메뉴에서는 두 파일을 함께 공유하며, 지원하지 않으면 각각 저장·첨부한다.

## 저장

Firebase 설정 없으면 `localStorage`의 `gdr-tennis-v1`에 저장한다. 이 브라우저·접속 주소에만 남으며 다른 기기와 공유되지 않는다. JSON 백업을 내려받아 보관할 수 있다. 같은 날짜를 덮어쓰는 백업 가져오기는 거부한다. 자동으로 Firebase에 업로드하지 않는다.

설정이 있으면 Firebase modular SDK와 Firestore 실시간 구독 사용. 연결 실패 시 로컬 저장으로 우회하지 않는다. 서버 확인 전 공유 저장 성공으로 표시하지 않는다. 점수 수정은 트랜잭션과 `revision`으로 다른 사람의 변경을 덮어쓰지 않도록 검사한다. 입력 중 서버 갱신이 와도 입력값을 유지한다.

```text
clubs/gdr/sessions/{YYYY-MM-DD}
  schemaVersion: 2, date, participantIds, fixedPlayerIds
  startTime, endTime, roundMinutes, partnerRepeats, lockedPairs
  guests?: { guest001: { name }, ... }
  roundCount, matchCount, createdAt

clubs/gdr/sessions/{YYYY-MM-DD}/rounds/{round}
  round, matchMap: { r1-c1: { round, court, teamA, teamB }, ... }

clubs/gdr/matchResults/{YYYY-MM-DD_r1-c1}
  date, matchId, scoreA, scoreB, outcome, revision, updatedAt
```

회원 신원은 `data/players.json`, 현재 분기 명단은 `data/periods.json`에 보관한다. ID는 GDR 전용이며 대포 ID와 분리한다. 과거 기록은 실제 경기 결과에서 다시 계산하므로 점수 수정이 중복 누적되지 않는다.

분기 순위와 선수 필터는 해당 분기의 명단 및 저장된 당시 멤버를 사용한다. 멤버 화면은 전체/등록된 분기 명단을 선택해 조회하며 가나다순과 성별 배경색을 유지한다. 현재 Firestore 생성 규칙은 2026년 4분기의 14명 범위이며, 다른 분기 명단을 등록해 운영할 때 서버 허용 명단도 함께 변경해야 한다.

게스트 ID는 모임 안에서만 식별한다. 다른 날짜에 같은 `guest001`이어도 이름과 신원은 합치지 않는다. 게스트 정보는 해당 모임 헤더에 저장하고 이름을 날짜별로 읽는다. `participantIds`는 회원+게스트, `fixedPlayerIds`는 해당 모임의 회원만 포함한다. 기존 게스트 없는 모임과 백업은 계속 읽을 수 있다.

모임 헤더와 모든 라운드를 한 트랜잭션으로 확정한다. 라운드 단위로 서버 검증해 시간이 길어져도 Firestore 규칙의 표현식 한도를 넘기지 않는다. 조회 시 헤더의 라운드·경기 수와 실제 라운드를 확인해 앱의 `schemaVersion: 1` 형식으로 재구성한다. 로컬 저장과 JSON 백업 형식은 유지하며, 기존 Firestore의 버전 1 모임도 계속 읽고 점수를 수정할 수 있다.

## Firebase 연결

연결 대상 프로젝트: **guldari**. 처음 확인한 Firebase CLI 업무 계정은 해당 프로젝트 권한이 없어 403을 반환했다. 제공받은 웹 앱 설정을 `.env.local`에 반영했다. 사용자가 2026-10-07 콘솔에 GDR 규칙을 게시해 공개 사이트의 공유 연결을 확인했다. 개인 Google 계정의 프로젝트 관리 권한도 확인했으며, 기존 기록은 이 권한으로 생성 전용 일괄 적재했다. 같은 날 이전 기록의 `historySets`·`historySources`·`historyImports` 조회 규칙도 게시했다. 이 세 경로의 클라이언트 쓰기는 계속 거부한다.

1. Firebase 콘솔 → 프로젝트 설정 → 일반에서 웹 앱을 등록하고 `firebaseConfig` 확인.
2. `.env.example`을 `.env.local`로 복사하고 웹 앱의 `apiKey`, `authDomain`, `projectId`, `appId`를 입력. 웹 앱 식별 설정이며 서비스 계정 비밀 키가 아니다.
3. Firestore 기존 규칙 확인 후 `firebase/firestore.rules`의 GDR 경로 규칙을 반영. 기존 다른 앱이 있으면 루트 규칙 전체를 덮어쓰지 말고 통합해야 한다.
4. 앱 재시작 후 공유 조회 확인. 규칙 반영 전 점수 쓰기는 실패할 수 있다.

사용자 요청에 따라 로그인 없이 조회·대진 생성·점수 입력한다. 규칙은 지정된 14명과 게스트 8명의 ID·이름·회원 구분·시간 범위·경기 필드·팀 구성·동시 중복 출전·점수 범위·결과 일치·서버 시각·수정 버전을 검사한다. 저장된 모임·라운드 수정·삭제와 결과 삭제, 다른 경로 접근은 거부한다. 로그인 없이 입력하므로 링크를 가진 사람의 신원을 구별할 수 없다. 서버 규칙은 모든 참가자의 총 경기 수를 직접 집계하지 않으며, 개인별 경기 수와 완전한 라운드 구성은 앱의 대진 검증에서 검사한다.

임시 Java 런타임으로 `demo-gdr` 로컬 Firestore 에뮬레이터에서 규칙 검증 통과. 익명 조회·대진 저장·점수 저장·0:0 무승부 수정 허용, 잘못된 점수·동시 중복 출전·허용되지 않은 필드·삭제·대진 변경·잘못된 수정 버전 거부 확인. 실제 프로젝트에는 시험 데이터를 쓰지 않았다.

## 대진 알고리즘

`src/scheduler.js`는 경기 수 배분과 팀 배정, `src/ratings.js`는 내부 배정값 계산을 담당한다. `data/strength-baseline.json`의 그룹 순서는 민종·상재 → 웅기·동주 → 남엽·성현 → 명렬·진우 → 진삼·수한 → 지원·명진 → 근화·재혁이다. 같은 그룹은 같은 초기값을 사용하며 0.9~0.1로 환산한다. 이 그룹은 초기 기준이며 자동으로 대회 준비 페어를 등록하지 않는다. 순서 변경은 JSON의 그룹 순서 변경으로 반영한다. 알 수 없는 초기값은 0.5다.

이번 모임 날짜보다 앞선 해당 분기의 완료 경기만 사용한다. 팀별 두 멤버의 초기값 평균으로 예상 승률 `1 / (1 + exp(-4 * (평균A - 평균B)))`을 계산하고 실제 결과(승 1, 무 0.5, 패 0)와의 차이를 개인별 평균 낸다. 이를 초기값에 더해 0~1로 제한한 분기 성적값을 얻는다. 파트너와 상대 구성을 고려하므로 쉬운 상대를 이긴 결과와 예상 밖 승리의 영향이 다르다. 경기 점수 차이로 평가값을 과하게 높이지 않는다.

최종값은 초기값과 분기 성적값을 `분기 경기 수² / (분기 경기 수² + 24²)`로 혼합한다. 4경기 약 3%, 12경기 20%, 24경기 50%. 초반 소량의 결과는 기준을 거의 바꾸지 않고 충분한 기록이 쌓이면 영향이 커진다. 각 사람의 경기 수로 신뢰도를 계산하며 참석 횟수나 누적 승점 자체가 실력 평가를 올리지 않는다. 기록이 없으면 초기값 유지. 다른 분기·미입력·모임 당일·미래 기록은 제외한다. 점수 수정 시 현재 결과 전체에서 다시 계산하며 중복 가산하지 않는다. 초기값은 분기 승점과 경기 수에 합산하지 않는다. 이 설정과 평가값은 회원 UI와 공유 저장 데이터에 표시하지 않는다.

맞붙는 두 팀의 평가값 차이와 팀별 합계 편차를 줄인다. 경기 수·시간·중복 출전은 필수 조건. 파트너 중복·상대 반복·연속 휴식도 함께 낮춘다. 확률 탐색이므로 전역 최적해를 보장하지 않는다. 평가값은 제시한 초기 기준과 경기 결과의 추정치이며 실제 실력의 절대 평가가 아니다.

## 대회 준비 페어와 표시

게스트의 내부 초기값은 사용자 요청에 따라 0.65다. 게스트가 포함된 완료 경기에도 이 기준을 사용해 회원 성적을 계산한다. 게스트 본인의 기록을 회원 평가나 다른 날짜의 동명 게스트로 누적하지 않는다. 이 값은 UI와 저장된 모임 데이터에 노출하지 않는다.

별도 `대회 준비` 화면에서 두 멤버를 눌러 페어를 등록·해제한다. 한 사람은 한 페어에만 등록한다. 설정은 기기 로컬에 보관하고, 확정 모임의 적용 페어는 `lockedPairs`에 함께 저장한다. Firestore에서는 중첩 배열을 지원하지 않으므로 `{ first, second }` 객체 목록으로 변환해 저장하고 조회 시 앱 형식으로 복원한다. 둘 다 참석하면 같은 경기 수로 함께 출전하도록 먼저 탐색한다. 참석 인원 때문에 전 경기 동반 출전이 불가능하면 동일 페어 출전을 우선하는 대진으로 재탐색한다. 예외는 화면에서 안내한다. 개인 경기 수를 바꾸면 등록 파트너의 경기 수도 함께 바뀐다. 대회 준비 페어의 의도된 반복은 일반 파트너 반복 횟수에서 제외한다.

멤버·참석자·페어 후보는 가나다순. 성별은 배경만 연파랑/연분홍으로 구분하고 이름 색은 동일하다. 실제 대진에서는 성별로 조를 제한하지 않는다. 코트 이름은 `안쪽`, `바깥쪽`. 평가 점수와 전력/균형 표현은 회원 화면에 표시하지 않는다.

조회 기본값은 한국 날짜 기준 현재 분기다. 조회 기간은 올해와 저장된 기록의 연도별 상반기·하반기·1~4분기, 날짜별 모임, 전체 누적, 시작일·종료일 직접 선택을 제공한다. 직접 선택한 기간은 양 끝 날짜를 포함한다. 회원·게스트 이름 검색은 전체 이름과 짧은 이름의 부분 일치를 지원하며, 순위 검색은 원래 기간 내 순위를 유지한다. CSV에는 검색된 회원을 내보내고 결과 이미지에는 검색과 무관하게 선택 기간의 전체 경기한 회원을 포함한다. 읽기 권한이 없으면 연결 대기 화면을 표시하고 순위나 CSV를 0점 기록으로 표시하지 않으며 기록 이미지 내보내기도 비활성화한다.
